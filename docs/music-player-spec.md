# 音乐播放器需求规格（Spec）

> 状态：方向已确定，待实现（2026-10-28）

## 1. 目标

实现 Apple Music 那样的歌词播放效果：逐字扫词、翻译与音译同屏、对唱与背景人声、流畅滚动与过渡动画，并给出一个完整可用的播放器页面（`/music`）。

交付范围就一个页面：`/music`。不扩张成音乐站。

参考实现：

- [amll-dev/applemusic-like-lyrics](https://github.com/amll-dev/applemusic-like-lyrics)：Web 端类 Apple Music 歌词组件的视觉效果与交互基准。
- [Mrs4s/StarryPlayer](https://github.com/Mrs4s/StarryPlayer)：歌词数据模型、多来源解析与对齐规则的工程基准。

### 1.1 参考原则：逻辑以 StarryPlayer 为准

- **逻辑层一律以 StarryPlayer 的代码逻辑为参考**：歌词解析与预处理、翻译 / 读音（音译）与主歌词的同步、歌词来源选择与缓存、当前行与高亮的判定（歌词展示策略）、播放队列与播放模式、进度时钟与会话恢复（播放策略）。设计或实现这些部分前，先查对应的 StarryPlayer 实现；行为有差异时以 StarryPlayer 为准，确需偏离的在本文档中注明原因。
- **界面与交互由我们自己设计**：功能与 StarryPlayer 大致对齐即可，界面外观、交互方式可以不同，并体现我们自己的风格（例如歌词来源标签用各平台自己的单色标志、歌单为右侧抽屉）。StarryPlayer 是 Swift 原生应用，其界面代码既不参考也无法复用；需要时只借鉴其动效表现（如弹簧、透明度、模糊的取值），用 DOM / CSS 自行实现。
- **许可证**：StarryPlayer 为 AGPL-3.0，本仓库为 MIT。只借鉴算法、规则与参数，按我们的数据结构自行实现；不复制、不逐行翻译其源代码，代码与注释中不出现其原文。

## 2. 歌词策略和歌词来源

### 2.1 总体策略

参照 StarryPlayer 的 `LyricsResolver`：歌词不按「谁先返回」决定，而是按**质量等级（tier）**决定，高等级胜出并原地执行升级；同一首歌只展示一份结果，不做逐行混拼。

优先级链（从高到低）：

1. **TTML**（逐字 + 翻译 + 音译 + 对唱 agent + 背景人声 + 段落，信息最全，一旦命中就整段胜出）。同一等级内再分两个子来源：**自定义 TTML 源**（优先，见 2.6）> **AMLL TTML DB**
2. **平台逐字歌词** —— 网易云 `yrc` / QQ `qrc` / 酷狗 `krc`，三家平级，按 2.3 的质量规则选择
3. **平台行级歌词** —— `lrc`，仅行时间，无逐字
4. 无歌词 —— 显示「暂无歌词」或纯音乐占位

硬规则：

- **优先逐字**：只要存在任一逐字来源，不得停留在行级。
- **只升不降**：允许先展示行级（快），TTML 到达后原地升级；升到 TTML 后不再回退。
- **宁缺勿错**：附加信息（翻译/音译）挂不上就丢弃，不用「最近一行」凑。

### 2.2 来源

| 来源 | 内容 | 获取方式 |
|---|---|---|
| 自定义 TTML 源（自建静态目录） | `.ttml`：同官方库，条目由自己维护 | 按配置的地址模板（`{id}` 为网易云歌曲 id）或 `{url_prefix}/{ncm_song_id}.ttml` 直取，见 2.6 |
| AMLL TTML DB（`amll-dev/amll-ttml-db`） | `.ttml`：逐字、翻译、音译、对唱 agent、背景人声、段落 | 按平台 id 直取 `{platform}-lyrics/{id}.ttml`，多镜像，后端缓存 |
| 网易云音乐 | `yrc` / `ytlrc` / `yromalrc`（逐字），`lrc` / `tlyric` / `romalrc`（行级） | 已有 `internal/service/music.go` 的 `GetLyric` |
| QQ 音乐 | `qrc`（逐字），`lrc`（行级），翻译（LRC）/ 音译（QRC）随接口返回 | **已实现**：`internal/service/music_qq.go`，按 2.3 匹配，见 7.2a |
| 酷狗音乐 | `krc`（逐字），`lrc`（行级），翻译 / 音译在 KRC 的 `[language:]` 中 | **已实现**：`internal/service/music_kugou.go`，按 2.3 匹配，见 7.2i |

> AMLL TTML DB 的实际布局（已核对）：`raw-lyrics/{时间戳}-{作者 id}-{hash}.ttml` 为原始文件，`{ncm,qq,am,spotify}-lyrics/{平台 id}.ttml` 为按平台 id 建立的同内容副本，另有 `metadata/raw-lyrics-index.jsonl`（每行 `{metadata, rawLyricFile}`）用于检索。**按 id 取词只需直取副本文件，不需要加载索引**（原来 2.3 的「必须缓存索引」结论作废）。

### 2.3 命中与匹配

- **自定义源**：最优先探测，URL 由配置的地址模板（或 `url_prefix`）与网易云歌曲 id 拼成，命中规则见 2.6。
- **AMLL 官方库**：按歌曲在各平台的 id 直接拼 `{mirror}/{platform}-lyrics/{id}.ttml`，命中 200 即用（已实测 raw.githubusercontent / jsDelivr / `amlldb.bikonoo.com` 三个镜像均可用；不存在的 id 前两者返回 404，`amlldb.bikonoo.com` 约 5 秒后返回 302）。目前只有网易云 id，取 `ncm-lyrics/{id}.ttml`。
  - 偏离 StarryPlayer：StarryPlayer 只有一个镜像模板；我们**并发请求全部镜像**，任一命中即采用，其余取消；两个镜像「确定未命中」即记负缓存（各镜像是同一仓库的副本，不必等 `amlldb.bikonoo.com` 约 5～8 秒后才返回的 302）。
- **平台侧**：有该平台 id 时直取；没有时用**标题 + 歌手 + 时长**打分匹配同一录音（当前音乐库只存了网易云 id，QQ / 酷狗的歌词要靠这一步才能用上）。匹配规则（同 StarryPlayer 的 `LyricCandidateMatcher`，`scoreLyricCandidate`）：
  - 归一化：小写，去掉空白、标点与符号。
  - 歌名须相同，或一方包含另一方且较短的一方不少于较长一方的 34%；时长都已知时相差不超过 20 秒，5 秒内为「时长接近」。
  - 有歌手时须有一位歌手相同或互相包含（至少 2 个字，候选的歌手按 `、&;，,/|·・` 拆分）；歌名不同时还须歌手匹配或时长接近。
  - 得分：歌名相同 10 / 包含 4，歌手相同 +5 / 包含 +2，专辑相同 +2，时长接近 +3；取最高分，同分取靠前的；没有合格的候选时视为没有匹配（宁缺勿错）。
- **全部请求、按质量选择**（偏离 StarryPlayer：它拿到逐字就停，我们网易云有逐字歌词也照样请求其余来源）：网易云、TTML、QQ 音乐、酷狗音乐**一开始就全部并发请求**，到齐的来源按质量排序（`lib/lyrics/resolve.ts`）：
  1. 等级：TTML > 平台逐字 > 平台逐行；
  2. 同一等级比来源**自带**的翻译与音译（各算一项，越全越好；借来的不算）；
  3. 仍相同时按 网易云（歌曲自己的平台，时间轴与播放的音频一致）> QQ 音乐 > 酷狗音乐。
  例如网易云只有逐字原文、QQ 音乐有逐字 + 翻译 + 音译时用 QQ 音乐；两边一样全时用网易云。读者固定了某个来源时用固定的来源。
  - 匹配到的 QQ 歌曲还会按 mid 查 AMLL TTML DB 的 `qq-lyrics/{mid}.ttml`（同 StarryPlayer：TTML DB 用各平台匹配到的 id 查询）；按网易云 id 收录的 TTML 优先。
- **确定未命中**：3xx（不跟随重定向）、404、410、正文不是 TTML（不以 `<` 开头、不是格式正确的 XML 或根元素不是 `tt`）。其余状态码、超时、网络错误为**出错**，不作为未命中缓存（同 StarryPlayer）。

### 2.4 升级与借补

- 所有来源**并发请求**；按 2.3 的质量规则选择，**只升不降**：先到的先上屏，更好的来源到达后原地替换（`lib/lyrics/resolve.ts`）。
- 防闪屏（同 StarryPlayer）：平台结果上屏前若 TTML 已到达，直接显示 TTML，不先闪一下平台歌词。
- 选中的来源（TTML 或平台歌词）**缺翻译 / 缺音译**时，向其余平台的歌词**借**，而不是因此改用别的来源：按时间与主唱行一对一挂载（宁缺勿错，容差 1 秒）；含中日韩文字的音译行不借（多为「以下音译由 AI 生成」之类的说明，同 StarryPlayer）。依次向网易云、QQ 音乐、酷狗音乐借（跳过自己），前一家缺的那一种再向后一家借。
- **去掉署名行**（同 StarryPlayer 的 `LyricsCreditStripper`，`lib/lyrics/strip-credits.ts`）：平台歌词首尾的「歌名 - 歌手」、「词：…」「作曲 : …」「Producer: …」、「未经许可不得翻唱」等；只去开头最多 16 行、结尾最多 8 行中连续的署名行，开头 3 行内单独的歌名或歌手行也去掉，不会把全部行去掉；TTML 不处理。
- QQ 音乐翻译中的 `//` 表示该行没有翻译，不挂载；QQ 音乐与酷狗音乐的纯音乐占位（「此歌曲为没有填词的纯音乐，请您欣赏」）按纯音乐处理。
- **按曲目固定来源（pin）**：读者可在歌词来源标签中为某首歌固定来源（存本地，最多 2000 首，超出淘汰最早的）；固定的来源没有歌词时回落到自动选择（同 StarryPlayer）。

### 2.5 缓存

参数同 StarryPlayer，后端进程内缓存（LRU），同一来源、同一 id 的并发请求合并：

| 内容 | 命中 | 确定未命中 | 出错 |
|---|---|---|---|
| TTML（自定义源、AMLL 分别缓存） | 长期（只受 LRU 淘汰） | 72 小时 | 不缓存 |
| 平台歌词（网易云） | 30 天 | 1 天（之后可能补上） | 不缓存 |
| 平台歌词（QQ 音乐 / 酷狗音乐，按网易云歌曲 id，含匹配结果） | 30 天 | 没有匹配或没有歌词 1 天；搜索有接口出错（降级）时只 1 小时 | 不缓存 |
| 按 QQ 歌曲 mid 收录的 AMLL TTML | 长期 | 72 小时 | 不缓存 |

### 2.6 自定义源（自建 TTML）

允许把自己整理好的 TTML 放到自有静态目录，作为一个与官方库同类型（AMLL/TTML）的歌词源，用来覆盖官方库未收录、或官方版本不满意的情况。

**定位**：

- 类型记为 `amll`（即 TTML 逐字格式），与官方库同一 tier，但**排在其前面**——同名先取自己的。
- 只做「按网易云歌曲 id 的覆盖」，不做跨平台 id 体系、不做搜索接口。

**寻址规则**：

```
{url_prefix}/{ncm_song_id}.ttml      # 配置为目录前缀时
任意含 {id} 的地址模板                  # 如 https://cdn.liteyuki.org/snowykami/music/lyrics/{id}.ttml、https://example.com/ttml?id={id}
```

- 由后端环境变量 `MUSIC_TTML_URL_PREFIX` 或后台「全局配置 › 前台 › 音乐播放器 › 自定义歌词源地址」（KV `music_ttml_url_template`）提供，**环境变量优先**：设置了环境变量时后台的该项显示为只读并注明（`GET /api/v1/admin/config/env-overrides` 返回被环境变量覆盖的配置项）。含 `{id}`（或 `{song_id}`）时视为地址模板，替换为歌曲的网易云 id（可以是任意链接风格）；
  不含 `{id}` 时视为目录前缀（例如 `https://static.example.com/ttml`），后端去尾斜杠后拼接 `/{id}.ttml`。
- 拼出的地址必须是 http(s) 绝对地址，否则视为未配置。
- 浏览器不直接请求自定义源：前端请求本站后端的 `/api/v1/music/song/:id/lyric/ttml`，由后端去自定义源与 AMLL 镜像取词、校验并缓存（避免跨域、统一缓存与未命中判定）。站长的源为 `https://cdn.liteyuki.org/snowykami/music/lyrics/{song_id}.ttml`。
- 一个 id 只对应一个文件，**没有索引文件，没有元数据**，命中判断完全靠 HTTP 状态。

**判定与容错**：

- `200` 且响应体以 `<` 开头、能被 TTML 解析器成功解析 → 命中，作为最高优先级结果使用。
- `404` / 其他非 2xx / 网络错误 / 解析失败 → 视为未命中，静默回落到官方库，不向用户报错。
- 请求需设超时、限制响应体大小（防止误配置拉回整页 HTML），只接受配置好的地址（id 只能是数字），不接受任何来自前端的任意 URL（避免 SSRF）。
- 不做重定向跟随；重定向一律当未命中。

**缓存**：

- 命中内容长期缓存，按 id 存。
- 确定未命中做 72 小时负缓存（见 2.5），避免每次播放都去探一次；更新文件后需等负缓存过期或重启后端。

**与完整策略的关系**：

- 自定义源命中即整份采用，不与官方库或平台歌词逐行混拼；缺翻译/音译时按 2.4 向平台借。
- 自定义源与官方库的探测可以并发；自定义源命中后丢弃官方库结果。

## 3. 非目标

### 3.1 不做

- **不做多用户**：没有账号体系、没有云端歌单、没有收藏/喜欢/播放历史/播放次数，不对不同访客展示不同内容。
- **不做播放列表管理**：不做建歌单、拖拽排序、增删歌曲、导入导出。播放列表就是在后台配置好的那一份，前端只读展示与播放。
- **不做其他页面**：不做艺术家页、专辑页、平台搜索页、排行榜、歌词站、歌词编辑器。整个音乐功能只有 `/music` 一个页面。
- **不做音乐平台搜索**：不调任何外部音乐接口搜歌、不接平台榜单、不允许用户搜索库外歌曲。只允许对已配置好的播放列表做**前端本地过滤**（见 8.11）。
- **不引入 AMLL 运行时**：不依赖 `@applemusic-like-lyrics/*`（AGPL-3.0 与本仓库 MIT 不兼容），只借鉴其视觉参数与数据模型，自己实现。
- **不自建歌词库平台**：自定义 TTML 源只靠静态文件目录（见 2.6），不做上传界面、审核、版本管理、多人协作。
- **不做桌面/移动客户端**：只做 Web 页面，不做 Tauri / App / 后台常驻播放。

## 4. 术语

| 术语 | 含义 |
|---|---|
| 播放器页 | `/music`，本规格交付的唯一页面 |
| 悬浮播放器 | 现有的全站悬浮球 + 弹出面板（`components/common/music-player.tsx`），与播放器页共用同一份播放状态 |
| 歌单 | 后台配置好的唯一一份播放列表（网易云歌单或静态 JSON），前端只读 |
| 歌词舞台 | 播放器页中滚动展示歌词的区域，即第 8 节描述的渲染效果 |
| 行 / 词 | 一行歌词由若干带时间的词组成；词是逐字擦除的最小单位（中日文通常为单字，拉丁文为单词） |
| 行组 | 一行主歌词连同附着在它上方或下方的背景人声行 |
| 逐字歌词 / 行级歌词 | 有词级时间（TTML、yrc、qrc、krc）/ 只有行时间（lrc） |
| 翻译 / 音译 | 译文（`tlyric` 等）/ 读音，如日语罗马音（`romalrc` 等） |
| 对唱（duet） | TTML 中 agent 不是主唱的行，右对齐显示 |
| 背景人声（BG） | TTML 中标为背景的行，字号更小、附着在主行上 |
| 间奏 | 相邻两行之间 ≥ 7000ms 的空隙 |
| 来源等级（tier） | 歌词来源的质量等级，见 2.1；高等级胜出，只升不降 |
| 音频时钟 | 全局 `<audio>` 元素的 `currentTime`，是播放进度的唯一来源 |

## 5. 功能需求

### 5.1 页面形态

- `/music` 为**沉浸式全屏页面**：不套用站点顶栏、侧栏与页脚，背景为封面驱动的动态背景（8.10）；左上角保留一个返回按钮（返回上一页，没有上一页时回首页）。
- 进入播放器页时隐藏悬浮播放器，离开后恢复；进出页面不打断播放、不重置进度。
- **桌面端（≥ 1024px）**：左栏为封面、曲名 / 歌手 / 专辑、进度条与控制栏；右栏为歌词舞台；歌单为从右侧滑出的抽屉。
- **移动端（< 1024px）**：单栏，在「歌词视图」（打开时默认）与「封面视图」之间切换（点击封面或歌词切换）；控制栏固定在底部；歌单为底部抽屉。
- 歌单为空或加载失败时显示空态，不渲染控制栏。

### 5.2 播放控制

- 播放 / 暂停、上一首、下一首、播放模式（列表循环 / 单曲循环 / 随机）、可拖动进度条、音量与静音。
- 键盘：空格播放 / 暂停，← / → 快退 / 快进 5 秒，↑ / ↓ 调节音量；焦点在输入框内时不响应。
- MediaSession（锁屏 / 控制中心）沿用全局播放器现有实现。
- 播放模式、音量、当前曲目与进度沿用现有的本地存储，与悬浮播放器共享。

### 5.3 歌词舞台

- 按第 8 节渲染；点击某一行跳转到该行开始播放；手动滚动期间暂停自动对齐，松手后回归（8.4）。
- **翻译与音译为两个独立开关**，可同时开启（同时开启时按 8.5 的顺序同时显示）；开关状态存本地，播放器页与悬浮播放器共用。
- 无歌词时显示「暂无歌词」；纯音乐显示纯音乐占位；歌词加载中显示骨架，行级结果先到先上屏，更高等级到达后原地升级（2.4）。

### 5.4 歌单面板

按 8.11：一次拉全、本地过滤、点击即播放、不改变队列；当前曲目在列表中高亮，打开面板时自动滚动到当前曲目。

### 5.5 悬浮播放器（播放器页的缩小版）

- 悬浮球（可拖动、贴边停靠）点开后是播放器页的缩小版：深色沉浸卡片，背景为模糊封面；封面、歌名、歌手与歌词来源标签，歌词舞台（同一歌词引擎的紧凑模式），控制栏（同一组件的紧凑模式）。
- 歌名与歌手（含专辑）超出宽度时以跑马灯滚动（悬停暂停，两端渐隐；减少动态效果时改为省略号截断）。
- 右上角按钮进入完整的播放器页 `/music`；歌单为从歌单按钮弹出的小浮层（含列表内搜索，点歌后收起，悬浮卡片保持打开），不使用播放器页的侧边抽屉。
- 紧凑模式只缩小字号、间距与间奏高度，焦点对齐位置为歌词区高度的 40%，按距离模糊减半；其余行为（逐字擦除、翻译与音译、点击跳转、手动滚动）与播放器页一致。
- 播放器页的歌名与歌手同样在过长时以跑马灯滚动。
- 播放时悬浮球以专辑主题色发光。文章内高单曲卡的歌词区同样使用紧凑模式，文字颜色跟随站点亮暗主题（`--lyric-color`）。

### 5.6 分享地址

- 播放器页的地址实时带上当前曲目与进度：`/music?id=网易云歌曲 id&start=开始秒数`，`start` 保留两位小数；播放中最多每秒更新一次，停下后写入最后的进度；用 `history.replaceState`，不产生历史记录；其他查询参数保留。
- 打开带参数的地址：歌曲在歌单内时定位到该曲目与进度（不自动播放，浏览器的自动播放限制）；不在歌单内时忽略参数。整页打开时由悬浮播放器的恢复逻辑处理，站内跳转时由播放器页处理。
- 本地存储的恢复策略不变：没有参数时仍按本地存储恢复上次的曲目与进度，播放中照常写入本地存储。

## 6. 非功能需求

### 6.1 性能

- **高频进度不进 React 状态**：播放进度不再放进 music context 的 value；只显示文字的地方（时间、进度条）订阅节流后的时钟（不高于 4 次/秒），歌词舞台在 `requestAnimationFrame` 中直接读音频时钟。
- music context 的 value 需 memo，播放进度变化不得引起全站使用 `useMusic()` 的组件重渲染。
- 歌词舞台逐帧动画只修改 `transform` / `opacity` / `filter` 与遮罩，不在逐帧路径上触发 React 渲染或布局（8.12）。
- 播放器页的代码（歌词引擎、TTML 解析）按路由拆分，不进入其他页面的包。
- 页面挂起后回归时单帧时间差钳制在 100ms（8.4）。

### 6.2 可访问性

- 所有控制有可读名称；进度条与音量为 slider 语义并可用键盘操作。
- `prefers-reduced-motion` 时关闭弹簧、模糊、词强调与阶梯入场，只保留整行高亮与瞬移滚动。
- 歌词文字与背景的对比度在最暗、最亮的封面配色下都需可读：动态背景之上统一加一层压暗遮罩。

### 6.3 可调参数

第 8 节标注「可调」的参数（羽化宽度、弹簧重量 / 刚度 / 阻尼、对齐锚点与位置、模糊上限、间奏阈值、提前起唱等）**集中定义为常量**（`web/src/lib/lyrics/config.ts`），不提供设置界面，也不进后台配置。

### 6.4 安全

- 自定义 TTML 源只接受环境变量中配置的前缀，不接受前端传入的任何地址；不跟随重定向，限制超时与响应体大小（2.6）。
- TTML 在前端用 `DOMParser` 以 `application/xml` 解析，只读取文本与时间属性，不把任何内容作为 HTML 插入页面。

### 6.5 兼容

- 不支持 `mix-blend-mode: plus-lighter` 时降级为单层高亮（8.2）；不支持 WebGL 时动态背景降级为 CSS 模糊封面。

## 7. 数据与接口

### 7.1 现有接口（沿用）

| 接口 | 用途 |
|---|---|
| `GET /api/v1/music/playlist` | 歌单曲目（含时长，静态歌单可无） |
| `GET /api/v1/music/song/:id/audio` | 播放地址，302 跳转到网易云临时地址；只对白名单内的歌曲开放（见 7.1a）。可选 `?level=standard\|higher` 要求较低音质（试听片段用 192k 的 higher，加载更快），只能低于或等于后台设置的音质，地址按歌曲与音质分别缓存 |
| `GET /api/v1/music/song/:id/audio/url` | 同一播放地址以 JSON 返回（`{url}`，同样只对白名单内的歌曲开放、支持 `?level=`），带 `Access-Control-Allow-Origin: *`：页面可以直接向网易云 CDN 按字节范围只加载需要的片段（如沙箱中的歌词特效演示页，见 `docs/prototypes/lyric-effects/showcase.html`） |
| `GET /api/v1/music/song/:id/lyric` | 网易云歌词（`lrc` / `tlyric` / `romalrc` / `yrc` / `ytlrc` / `yromalrc`），即平台等级的歌词 |

### 7.1a 站内播放的白名单

播放地址（`/song/:id/audio`）用站长的网易云账号换取，只对白名单内的歌曲开放，避免后端被当成任意歌曲的播放代理（`service/music_whitelist.go`）：

1. 登录的管理员与编辑：任何歌曲（写文章、预览草稿时要能试听，不能把自己拦住）。
2. 博客歌单中的歌曲。
3. 公开的文章与页面中引用的网易云歌曲：从已发布正文（`content`，不含草稿与私密内容）里的网易云单曲卡（`neteaseSong`，`mode` 为 netease 或旧数据没有 mode）与网易云歌词摘录（`lyricQuote`，`source` 为 netease）提取歌曲 id。扫描结果缓存 10 分钟；查不到某首歌且距上次扫描超过 30 秒时立即重新扫描，新发布的文章第一次播放就能生效。

- 白名单之外的歌曲返回 404（`music_song_not_found`）；在白名单内但网易云没有版权或账号无权播放时为 `music_song_unavailable`。歌曲信息、各来源歌词、副歌片段不受限制。
- 单曲接口（`/song/:id`）返回 `playable`：当前访客能否在站内播放。文章内的单曲卡与歌词摘录据此决定显示播放按钮还是「在网易云打开」；不在歌单内但可以播放的歌曲，点播放时插到当前曲目之后播放（`playSong`），也会出现在播放列表中（刷新后恢复为歌单）。
- 歌词标注（消耗大模型额度）只按 2、3 开放，不随登录身份放开。
- 不采用「前端签名 + 混淆」：浏览器能算出的签名，别人用无头浏览器或抠出函数就能复用，挡不住；可靠的控制只能在服务端。

### 7.2 新增：TTML 歌词

`GET /api/v1/music/song/:id/lyric/ttml`（公开，`:id` 为网易云歌曲 id）

- 后端并发探测：自定义源（`MUSIC_TTML_URL_PREFIX` 的地址模板或 `{前缀}/{id}.ttml`）与 AMLL TTML DB 全部镜像 `{mirror}/ncm-lyrics/{id}.ttml`；按优先级取第一个命中（自定义源优先，命中后不等 AMLL）。
- 可选参数 `source=custom|amll`：只取某一来源（供手动切换使用）；为空时自动选择。
- 命中：`200`，`{ "source": "custom" | "amll", "ttml": "<tt ...>...</tt>" }`；均未命中：`404`（`lyric_not_found`）。
- 后端只做探测、校验（以 `<` 开头、格式正确的 XML、根元素为 `tt`）与缓存，不把 TTML 转换为其他结构；解析在前端（`lib/lyrics/parse-ttml.ts`）。
- 配置：
  - `MUSIC_TTML_URL_PREFIX`（环境变量，可选）或后台配置 `music_ttml_url_template`（环境变量优先）：自定义源的地址模板（含 `{id}` / `{song_id}`）或目录前缀，都未配置时跳过自定义源。自定义源的缓存按完整地址区分，后台改了地址后立即按新地址探测。
  - AMLL 镜像列表为后端常量（raw.githubusercontent / jsDelivr / `amlldb.bikonoo.com`）。
- 缓存见 2.5。单次请求超时 8 秒（同 StarryPlayer），响应体上限 1 MB，不跟随重定向。

### 7.2a 新增：QQ 音乐歌词

`GET /api/v1/music/song/:id/lyric/qq`（公开，`:id` 为网易云歌曲 id）

- 后端取网易云单曲信息（歌名、歌手、专辑、时长），在 QQ 音乐搜索后按 2.3 的规则选出同一首歌，再调用 `GetPlayLyricInfo` 取正文、翻译与音译。
- 搜索分两轮（`searchQQSong`）：
  1. 客户端搜索（`u6.y.qq.com/cgi-bin/musics.fcg` 的 `DoSearchForQQMusicDesktop`，每页 20 条，带完整的歌名、歌手、专辑与时长），关键词「歌名 歌手」。该接口要求客户端签名（`music_qq_sign.go`，按协议行为自行实现）：请求头 `Sign` 为 12 个随机大写字母 + 对请求体的 HMAC-SHA1 摘要，`Mask` 为用 `Sign` 派生的密钥对「客户端版本 & 时间戳 & uid」做 QQ TEA 加密；`comm` 中带匿名会话（`GetSession` 取得的 uid / sid，进程内缓存 1 小时）。出错时最多重试 2 次（间隔 0.3 秒、0.6 秒）。
  2. 第一轮出错或没有合格候选时，**并发**尝试：客户端搜索只用歌名；联想搜索（`smartbox_new.fcg`，以「歌名」「歌名 第一位歌手」「歌名 全部歌手」三个关键词各搜一次，再用 `CgiGetTrackInfo` 批量补上时长、专辑与歌手）。各路候选按 mid 去重后统一打分。旧的网页公开搜索（`client_search_cp`）与客户端搜索数据相同，但现在基本只返回 500、且常要 5 秒才返回，不再使用。
- 第一轮出错（降级）且最终没有匹配时，未命中只缓存 1 小时（见 2.5），避免接口偶发故障让一首歌一天都没有 QQ 歌词。
- 正文与音译为十六进制密文：QQ 音乐客户端的三重 DES 变体（与标准 DES 有三处不同，见 `music_qrc.go`）解密后再 zlib 解压；QRC 去掉 XML 外壳（取第一个 `LyricContent` 属性，以 `"/>` 结束）。
- 返回：`200`，`{ "song_mid", "format": "qrc" | "lrc", "lyric", "translation", "romanization", "ttml"? }`；没有匹配且没有 TTML 时 `404`（`lyric_not_found`）；QQ 音乐接口出错时 `502`（`music_lyric_source_failed`）。解析在前端（`parseQqLyrics`）。
- 缓存见 2.5，同一首歌的并发请求合并；单次请求超时 10 秒。

### 7.2i 新增：酷狗音乐歌词

`GET /api/v1/music/song/:id/lyric/kugou`（公开，`:id` 为网易云歌曲 id，支持 `refresh=1`）

- 搜索：移动端公开搜索接口（`mobilecdn.kugou.com/api/v3/search/song`），并发以「歌名 歌手」与「歌名」各搜一次，候选按 hash 去重后按 2.3 打分。
- 取词：按歌曲 hash、关键词与时长调用 `lyrics.kugou.com/search` 取歌词候选，再以 `download`（`fmt=krc`，没有逐字时 `lrc`）取正文。
- KRC 解密：去掉 `krc1` 头，与 16 字节固定密钥循环异或后 zlib 解压。KRC 的字时间相对于行首，后端转换为绝对时间的 QRC；`[language:]` 中的 base64 JSON 含翻译（type 1，每行一句，转为 LRC）与音译（type 0，每字一个音节，转为带逐字时间的 QRC）。
- 返回：与 QQ 音乐相同的格式 `{ "hash", "format": "qrc" | "lrc", "lyric", "translation", "romanization" }`，前端直接用 `parseQqLyrics` 解析；没有匹配或没有歌词时 `404`（`lyric_not_found`）；接口出错时 `502`。
- 缓存见 2.5（与 QQ 音乐相同，含降级时的短未命中缓存）。

### 7.2b 新增：歌词标注（大模型辅助）

`GET /api/v1/music/song/:id/lyric/annotations`（公开，`:id` 为网易云歌曲 id）

- 目的：补足浏览器分词的不足，并为强调特效（8.2）挑选值得强调的词句、特效类型、每行的情绪基调与副歌行。**标注只引用歌词原文，不含也不改变任何时间轴**；时间一律取自歌词本身。
- 懒处理：读者播放到某首歌（且开启了歌词特效、歌词是逐字的）时，前端才请求；还没有标注时后端开始生成并返回 `{ "status": "pending" }`，前端每 2 秒再取一次，最多等 3 分钟。
- 生成：用站点配置的大模型（与 AI 摘要相同的配置与全局并发限制），输入为带行号的歌词文本（网易云逐字 > 网易云逐行 > QQ 音乐 > 酷狗音乐，去掉时间标签，最多 150 行），要求只输出 JSON：`{"lines":[{"i":行号,"mood":"bright","chorus":true,"phrases":[{"text":"原文片段","effect":"swell","color":"gold"}]}]}`；`color` 可选，只用于带颜色联想的意象；`scene` 可选，为写到具体画面的行选择全屏粒子场景，全曲最多 4 处。
- 校验（不合格的条目一律丢弃）：行号必须存在；短语必须是该行原文的连续片段（忽略空白、标点与大小写）、最长 12 个字；每行最多 2 个短语，全曲短语总数不超过「行数 / 2 + 4」；情绪只能是 calm / bright / sad / intense，特效只能是 swell / glow / wave / shake / focus（未知的特效改为 swell），场景只能是 petals / sparks / snow / stars / bubbles / rain（未知的丢弃），颜色只能取 32 色语义化色板中的名称（如 starry-blue 星空蓝、violet 罗兰紫，定义在后端 `lyricAnnotationPalette`，名称、中文名与意象写进提示词，色值在前端 `lib/lyrics/colors.ts`；旧版 8 色名称映射到最接近的新颜色，未知的颜色丢弃）。同一文本的行合并为一条。
- 返回：`{ "status": "ready", "stale"?, "font"?, "spotlight"?: { "text", "occurrence" }, "lines": [{ "text": 行原文, "mood"?, "chorus"?, "chorus_start"?, "scene"?, "scene_color"?, "phrases": [{ "text", "effect", "color"?, "font"?, "styles"? }] }] }`
- 上下文（`music_annotation_context.go`）：除歌词外，用户消息还带上歌曲信息（博客歌单曲目的歌名、歌手、专辑、别名 / 描述）、逐行中文翻译（与所选歌词同一来源，按开始时间在 1 秒容差内对齐，附在行末〔译：…〕，不参与歌词哈希）与网易云热评（`/comment/hot`，按点赞取前 5 条、每条最长 140 字，只在生成时拉取，失败时不带）；提示词要求热评只作低可信度参考、偏离歌曲的忽略，引用只能取自原文。
- 生成分两步（`music_annotation_pipeline.go`），避免一次输出整首歌的标注太慢：① 全曲规划（一次请求，输出很短）：主题、方向、副歌、意象对照表（imagery：核心意象与统一的 effect / color）、导语、尾奏热评、时刻、全曲字体、每行情绪与粒子场景；② 逐段标注：歌词按约 20 行一段（最多 6 段）并行请求，每段带着规划（方向、意象对照表、本段的副歌与情绪）、本段歌词与前后各 2 行（上下文），只输出本段的短语；全曲规划失败（调用出错、回复中没有 JSON 或解析失败）时等待 2 秒重试一次（等待不占用并发名额），仍失败则整个任务失败；某段失败重试一次，仍失败则这段没有短语。两步结果按行号合并成与单次生成相同的 JSON，再经过同一套校验。每次模型调用各自排队等待全局 AI 并发名额。提示词见 `music_annotation_prompt.go`：两步各用一份系统提示词，只放本任务需要的规则（规划不含短语字形规则，逐段不含导语、时刻、场景与情绪的规则），色板、字体与场景由数据表生成，用户消息中的标签与系统提示词同一种语言。
- 提示词语言与精简（`music_annotation_eval_test.go` 实测，`NEO_PROMPT_EVAL=1` 时运行：用本地数据库的模型配置与歌单，统计 token、无效短语、长音颤音、副歌命中、导语合规等指标，再让模型开启思考做 A/B 盲评）：与旧版（两步共用一份约 4400 token 的完整规则、逐段带完整歌词）相比，输入 token 减少约 52%（每首歌约 17800 → 8600）、输出减少约 46%、耗时约 10.5 → 7.2 秒。同内容的中英文两版对比（8 首歌、两轮共 56 次盲评）：英文胜率 62.5%，输出 token 少约 31%，耗时少约 18%，且中文版在日文歌上会从中文翻译里取短语，因此使用英文提示词，只要求导语与时刻的文字用简体中文。
- 特效分类（提示词中的 effect 部分，场景演示见 `docs/prototypes/lyric-effects/categories.html`）：按这几个字在「做什么」分组——grow 放大·起伏（swell / heartbeat / wave）、tremble 抖动（shake：有〔长音〕时为颤音，否则为呐喊）、light 光效（glow / shimmer）、focus 聚焦·镜头（focus；镜头推近与聚光灯由播放器按规划自动演出）、vanish 消失（dissolve 慢慢散去 / shatter 一下子碎掉），每种特效只保留一句话含义。实测（7 首歌，每轮 baseline 1 次、新版 2 次，共 3 轮 42 次盲评）：把每类的使用场景与示例短语写进提示词时模型更爱堆特效（「主歌偏满」「特效重叠」），两轮盲评 10:18 落后；只按类别分组的精简版盲评 8:6 领先，长音用颤音 52%→69%、普通句尾误用 shake 26%→8%，提示词长度基本不变，因此提示词只放分组，场景与示例留在原型页。逐段标注时聚光灯那一行标上 `spotlight`，要求最多 2 个简单短语（颜色、粗体、一个 swell 或 glow），不叠心跳、流光与多层辉光。
- 提示词写法（参考 Anthropic 的提示词建议，AI 摘要与 AI 写作的提示词同样按此调整）：规则附上原因（模型知道为什么才能举一反三）、尽量说「怎么做」而不是「不要做什么」、用户消息的各部分用 XML 标签分块（`<song>`、`<listener_comments>`、`<lyrics>`、`<plan>`），要做的事放在用户消息最后。实测（3 首歌各生成 1 次、6 次盲评，旧版结果用 `NEO_EVAL_BASELINE_RESULTS` 复用，不重新生成）新版 4:2 领先，评审的理由多为「更克制、层次更清楚」，长音颤音 100%。教训：把「普通句尾不要用 shake」改写成「普通句尾更适合 swell 或 glow」时，模型把建议当成了指令，swell 从 13 处增加到 38 处、盲评 2:4 落后；正面改写只描述目标，不顺手推荐替代做法。
- 校验时的统一处理（`sanitizeLyricAnnotations`，与提示词语言无关）：同一意象全曲一致——短语与规划意象对照表中的词相同时，特效与颜色一律按规划；其余短语在全曲再次出现时沿用第一次的特效与颜色；消散、破碎、流光、心跳是点睛之笔，全曲每种最多 3 处，超出的换成相近的常规特效（消散、流光换成 glow，破碎换成同样有冲击感的 shake，心跳换成 swell）；短语总数上限为「行数 × 2 + 6」（每行本来最多 3 个，原来的「行数 + 6」会把歌尾副歌的短语砍掉）。
- 长音与颤音：送给模型的歌词按逐字时间（网易云 YRC、QQ 音乐 QRC、酷狗转换后的 QRC）找出每行唱得最长、且不短于 1.5 秒的音节（实测普通音节中位数 0.2～0.4 秒），在行末标〔长音：「た」2.1 秒，句尾〕；提示词要求这些地方（尤其句尾的尾音、Ahh 一类的吟唱）多用 shake 表现颤音，短语包含长音所在的字，唱多久就颤多久。送去标注的是逐行歌词（网易云只有逐行，多数歌如此）时，生成时向 QQ 音乐 / 酷狗的逐字歌词借长音：开始时间相差 3 秒内且文字一致（忽略空白与标点）的行才借，送去标注的歌词文字不变（已有标注不会因此失效）。
- 思考强度：两步都以 `reasoning_effort: "none"` 关闭模型的思考。思考型模型（如 deepseek-flash）默认的思考内容是正式输出的 3～9 倍（实测规划约 9000 个思考 token），是生成慢的主要原因：关闭前一首歌 70～145 秒，关闭后 10～20 秒，标注质量相当（提示词已给出完整步骤与约束）。不支持该参数的接口返回 400 时去掉参数重试一次，并记住该接口与模型（`chatCompletionWithReasoning`）。每次生成在日志中记录规划与逐段标注各自的耗时。
- 热评过滤（`isLowQualityComment`）：拉取 50 条后过滤广告与链接、抢楼打卡（较短时）、刷屏笑声、几乎只有一两种字、去掉表情与 @ 后不足 6 个字的评论，再按点赞取前 12 条给模型。
- 提示词以「深情、敏感又大胆的演出导演」为角色，附情感与演出的对应参考（伤感、喜悦、激昂、温柔），采用 SOP：模型先在 JSON 中写下 `theme`（主题与情绪走向）与 `direction`（主色、特效风格、字体基调），再结合自身对这首歌的了解标出每段副歌的起点（`chorus_start`），最后逐行设计；`theme` / `direction` 只用于引导，不保存。温度 0.9；每行最多 3 个短语，全曲短语不超过「行数 + 6」，粒子场景最多 6 处，换字体的短语最多 10 处。
- 字体（全曲 `font` 与短语 `font`）：song 宋体、kai 楷体、xingkai 行楷、fangsong 仿宋、round 圆体、mono 等宽、script 英文花体。字体栈按「系统字体 → 自托管网页字体 → 通用字体」逐字回退：有系统字体（如 macOS 的宋体）时直接使用，手机（iOS / Android 不带这些中文字体）与没有下载可选字体的电脑才使用网页字体（`lib/lyrics/lyric-fonts.ts`：思源宋体、霞鹜文楷 Screen、智莽行书、站酷小薇、站酷快乐体、Dancing Script，npm 包随站点打包）。体积控制：每种只引入一个字重、只用 woff2、按 unicode-range 分片，浏览器只下载歌词里用到的字所在的分片（一首歌整曲用网页字体约 0.5～1.4 MB，只给短语换字体时通常几十 KB，分片可长期缓存、跨歌曲复用），`font-display: swap`；省流量模式或网络为 2G 及以下时不使用网页字体（`lyric-player--no-webfonts`，经 `--lyric-wf-*` 变量从字体栈中去掉）；字形 `styles`：bold、italic、underline，下划线在演唱时逐字画出（删除线已去掉：被否定、放弃的词改用 dissolve 消散，旧标注中的 strike 校验与前端都会忽略）。唱不满 0.6 秒的短语不做动效，但保留颜色、字体与字形。
- 副歌起点：该行强调强度 ×1.4，播放器页背景在开唱时爆发一次（0.2 秒亮起、1.8 秒回落）。
- 保存格式：`{ "font"?, "lines": [...] }`；旧版记录为 lines 数组，读取时兼容。
- 演出：shake 演唱时字快速细微地抖动；focus 在高亮行内先模糊、唱到时变清晰。播放器页（`/music`）另有全屏特效（`MusicStageEffects`，信号计算见 `lib/lyrics/stage-effects.ts`）：唱到 swell / shake 时背景呼吸亮起，唱到带颜色的短语时背景泛起该颜色，`scene` 从标注行开始持续 8 行（或到下一个场景）全屏飘落粒子（`lib/lyrics/stage-particles.ts`）。悬浮播放器与文章内单曲卡只有字词级效果；关闭歌词特效或系统要求减少动态效果时全部不演出。；前端按行文本（归一化后）匹配到当前显示的歌词上，因此与歌词来源（TTML / QQ / 网易云）无关。
- 持久化：表 `lyric_annotations`，按「歌曲 id + 歌词文本 SHA-256」唯一；歌词文本变化后重新生成。
- 有效期：后台「AI」中配置（`lyric_annotation_ttl_days`，默认 7 天，1～365）。过期后接口仍返回旧结果并标记 `stale: true`，同时在后台重新生成，前端先用旧结果并继续轮询；生成成功后覆盖原记录（`created_at` 为本次生成时间），失败时继续使用旧结果，30 分钟后再试。
- 手动刷新：`POST /api/v1/music/song/:id/lyric/annotations/refresh`（仅管理员），立即重新生成并返回 `pending`；播放器页歌词来源标签旁有仅管理员可见的刷新按钮。叠加了标注时，歌词来源标签最前面显示 AI 标志。
- 手动编辑（后台「音乐 → 歌词特效」，仅管理员，前后端都限制）：列表 `/console/lyric-effects` 列出博客歌单中的歌曲与已有标注的歌曲（`GET /api/v1/music/lyric/annotations`），显示未生成 / AI 生成 / 手动编辑过、特效数与时间，可按歌名、歌手或 ID 搜索，不在列表中的歌曲（文章引用）可按网易云 ID 打开。编辑器 `/console/lyric-effects/:id`（`GET /api/v1/music/song/:id/lyric/annotations/editor` 返回送去标注的完整歌词与当前标注，`PUT /api/v1/music/song/:id/lyric/annotations` 保存）沿用文章编辑器的气泡菜单与工具栏样式，但只能选区加特效，不能改歌词与时间轴：歌词按去重后的行显示（同一文本的行共用一条标注，左侧标出行号、重复次数、副歌、情绪、场景与聚光灯），选中一行中的文字弹出气泡工具栏，选择特效（按五类分组，附一句说明）、颜色、字体、粗体 / 斜体 / 下划线与节奏后添加（替换与选区重叠或同文本的旧短语；短语在行内每次出现都演出，同播放器），点击已有短语修改或删除，悬停用简化的 CSS 动画预览特效；右侧为当前行（情绪、副歌、副歌起点、粒子场景与颜色、聚光灯是这一行第几次出现）与全曲设置（字体、节奏、导语与当前聚光灯），表单由 react-hook-form 统一管理，有未保存的修改时离开页面前提示。保存时后端整体校验（`sanitizeEditedLyricAnnotations`：行必须是原文、短语是该行的连续片段且不重复、各取值合法、导语不超过 60 字、聚光灯指向存在的行；不合法时拒绝保存而不是静默修正，手动编辑不限制特殊特效与场景的数量），保留时刻与尾奏热评，记下 `edited_at`。手动编辑过的标注不再因过期自动重新生成；编辑器与播放器的「AI 重新生成」都会先确认（播放器暂停时还没取过标注，点击时先查询是否编辑过），重新生成后清空 `edited_at`。保存后本页播放器已取过的标注会重新获取。
- 限制：只为博客歌单内的歌曲生成（网易云歌单；静态歌单无法在后端校验，不提供），未配置大模型时返回 404（`lyric_annotations_unavailable`）；生成失败后 30 分钟内返回 404（`lyric_annotations_failed`），之后再请求会重试。

### 7.2d 新增：播放器页的温度

- 前奏导语、关键节点的「时刻」与尾奏热评（`lib/lyrics/moments.ts`，显示在歌词区底部，不挡歌词）：歌词标注新增 `intro`（模型写给听众的一句导语，40 字以内）、`outro_comment`（从热评中挑最贴合的一条的编号，后端换成 `outro: { content, liked }`）与 `moments`（4～5 个关键节点：情绪转折、副歌开始、最打动人的一句；优先挑与这一刻呼应的热评，没有合适的再写旁白；后端保存为 `{ text, occurrence, content, source: "comment" | "ai", liked? }`，前端按行文字的第 occurrence 次出现匹配到歌词行）。热评给模型 12 条（按点赞），同一条不重复使用（含尾奏）。
  - 开关：控制栏的「评论与旁白」按钮（翻译、歌词特效旁边，播放器页与悬浮小窗共用）可以隐藏导语、时刻与尾奏热评，默认开启；读者关掉后记在本地（localStorage `music-show-lyric-moments`），下次打开仍然关闭。歌词标注照常获取，字词特效不受影响。
  - 时机：时刻在对应行开唱时显示 9 秒，遇到下一个时刻或尾奏提前让位，优先级最高；导语从开播 0.3 秒显示到开唱前 0.6 秒，前奏较短时也至少显示 8 秒；尾奏热评在最后一句唱完 0.8 秒后显示，直到歌曲结束前 0.3 秒。
- 主题色：全曲规划时模型按歌曲的情绪与意象自由选一个主题色（`accent`，`#rrggbb`，不受封面限制，提示词只要求在深色背景上发光好看），后端只校验格式；后台编辑器可修改或清除。播放器页与悬浮小窗把它写入 `--lyric-accent`（`useSongAccent`），作为歌词辉光与背景呼吸的默认颜色。
- 封面取色（没有主题色时的回退）：从封面缩略图（网易云 `?param=48y48`，CDN 支持 CORS）按色相加权挑主色并提亮（`lib/lyrics/cover-color.ts`）；读取失败或封面近乎无彩色时不设置。
- 跟随鼓点的呼吸：Web Audio 分析低频能量，能量明显高于近期平均时轻轻亮一下背景（`lib/lyrics/audio-beat.ts`）。音频元素接入 Web Audio 后无法撤回，且非 CORS 音频接入后会被静音，所以只在以下条件全部满足时接入：播放器页、歌词特效开启、未要求减少动态效果、桌面端（`pointer: fine`）、歌单全部是站内代理的网易云音频；在用户手势中开启，之后加载的曲目带 `crossOrigin="anonymous"`（网易云 CDN 返回 `Access-Control-Allow-Origin: *`），暂停中的当前曲目带上 CORS 重新加载并回到原进度，正在播放的从下一首开始生效。

### 7.2h 新增：重新获取歌词

读者可以在歌词来源标签的菜单里（始终可点开）或「暂无歌词」下方点「重新获取歌词」：所有来源（网易云、TTML、QQ 音乐、酷狗音乐）都带 `refresh=1` 重新请求。

- 后端：带 `refresh=1` 时跳过缓存中「没有歌词」的记录（网易云的占位歌词、TTML 的确定未命中、QQ 音乐 / 酷狗音乐的没有匹配或没有歌词）重新向上游获取，已命中的歌词照常使用缓存；同一首歌的同一来源 30 秒内只绕过一次缓存（`music_lyric_refresh.go`）。
- 前端（`refreshSongLyrics`）：请求期间把当前已有的各来源结果当作快照补位，歌词不会消失、来源标签显示加载；新结果到达后原地替换，某个来源这次失败时沿用之前的结果。

### 7.2e 新增：歌词缓存

`GET /api/v1/music/song/:id/lyric/cache`（公开）：最近一次选出的最佳歌词快照 `{ "kind": "ttml" | "ncm" | "qq" | "kugou", "ncm"?, "ttml"?, "qq"?, "kugou"? }`（各来源与对应接口的返回相同，网易云歌词总会附带，供翻译借用与单行歌词），没有或超过 30 天时 404（`lyric_cache_miss`）。
`POST /api/v1/music/song/:id/lyric/cache`（公开）`{ "kind" }`：上报选出的最佳来源。

- 内容由后端用自己获取的来源数据写入（`GetLyric` / `GetTTMLLyric` / `GetQQLyric` / `GetKugouLyric`，均有内存缓存），不接受前端上传的歌词，避免缓存被写入假歌词；胜出的来源在后端没有歌词时不保存。
- 前端（`contexts/song-lyrics.ts`）把快照作为第四个并发请求：某个来源还在请求中或失败时先用快照中的同一来源补位，打开即显示最佳歌词，实时结果到达后原地替换；各来源都到齐后上报按等级最好的来源（不受读者固定的来源影响），同一页面内同一结果只报一次，所以每次播放都是对快照的一次更新。
- 表 `lyric_caches`（按歌曲 id 唯一），与歌词标注 `lyric_annotations` 分开保存，互不影响。

### 7.2j 镜头推近（播放器页）

每段副歌的第一行（`chorus_start`）开唱时，与副歌爆发同时触发：约 0.45 秒缓出地推近，再在 2.6 秒内缓缓回落（`stage-effects.ts` 的 `push` 信号）。`MusicStageEffects` 把推近程度写入页面根元素的 `--stage-push`（0 ~ 1），各层按不同倍数放大以产生景深：动态背景 ×6%、歌词区 ×4%、特效层（光晕与粒子）×8%（越靠前放大越多）。用 CSS `scale` 属性，只走合成，不触发布局与歌词引擎的尺寸重算；悬浮小窗不推近；关闭歌词特效或减少动态效果时不演出。

### 7.2k 聚光灯（点题句）

全曲规划时模型选出 1～3 句最点题的句子（`spotlights`：行号列表，歌名句或最深的告白，各句文字不同、唱满约 2 秒以上；多一句就少一分稀有感，第二、三句只在同样关键时才加；没有特别突出的就不选）。后端按行文字去重后保存文字（最多 3 句），**同一句的每次出现都演出**（副歌重复的点题句每次唱到都放大）；前端用 `resolveSpotlights` 把文字匹配到所有出现的主唱行。旧版只有一句的记录（`spotlight: {text, occurrence}`）读取时并入 `spotlights`。逐段标注时本段中所有聚光灯行都标上 spotlight。
强度包络（`stage-effects.ts` 的 `spotlightAt`，歌词引擎与舞台层共用）：每次开唱前 0.2 秒开始、0.5 秒内缓入亮满，保持到这一句唱完，再在 0.6 秒内回落；多句时取此刻最亮的一次，相邻两次（如连续重复的点题句）交接时不熄灭，歌词引擎换到另一句时重新测量放大倍数。

- 歌词引擎：整体平移使这一句移到歌词区垂直中央并放大到 1.25 倍（紧凑模式 1.1 倍；以行首为原点，放大后不超出行尾，按文字实际宽度限制，见 `spotlightFit`）；其余行不消失，只向两侧让开 0.75em（紧凑 0.35em）、不透明度降到 0.24、模糊至少 2.5px。
- 点题句保持清晰：这一句本身不加 drop-shadow（暖光由舞台层打在身后）；点题句几乎总带着强调短语（模型会把最重要的一句标得最重），整行放大后字的辉光会连成一片显得发虚，因此聚光灯亮起时按强度收敛这一句的字词特效：辉光降到 30%、字的放大幅度减半，颜色、字体与字形不变。
- 舞台层（`MusicStageEffects`）：歌词区中央一团暖光（不透明度 0.22，宽屏时在右侧歌词区）与很轻的四周压暗（0.18）。原型中更暗的「原版」画面发黑，改用此柔和版。
- 关闭歌词特效、减少动态效果与手动滚动歌词时不演出；悬浮小窗同样演出（放大与让开更小）。
- 后台编辑：行设置里的「聚光灯」开关（已有 3 句时其他行不可再开），全曲设置列出已选的句子，可逐句取消。

### 7.2l 歌词整体偏移（管理员微调，对所有人生效）

部分来源的时间轴整体偏早或偏晚时，管理员在播放器页歌词来源标签旁的「歌词偏移」（仅管理员可见）按 ±0.1 / ±0.5 秒微调，范围 ±10 秒；调整立即在本地生效，停止调整 0.6 秒后保存（`PUT /api/v1/music/song/:id/lyric/offset`，仅管理员）。偏移按歌曲与歌词来源（`ResolvedLyrics.source`，如 `ncm-yrc`、`qq-qrc`、`ttml-custom`）分别保存在表 `lyric_settings`（歌词的人工设置，与歌词标注、歌词缓存分开保存，以后其他人工设置也放在这里），因为不同来源的时间轴不同；为 0 时删除记录。读取接口 `GET /api/v1/music/song/:id/lyric/settings` 公开（所有人播放时都要用到）。前端在全站共用的歌词选择（`contexts/song-lyrics.ts`）选出来源后，按该来源的偏移平移所有行与词的时间（`lib/lyrics/offset.ts`，正数推迟、负数提前），再计算强调、间奏、时刻与舞台特效，所以播放器页、悬浮播放器、导航栏与文章内的单曲卡都按同一偏移显示。逐字音译（`romanizationWords`）有自己的时间，与行、词一起平移（早期版本漏了它，偏移后罗马音与原文错开）。

### 7.2n 全站默认歌词来源（管理员选择）

歌词来源标签的菜单对所有人开放。读者选择某个来源只保存在本地（localStorage `music-lyric-pins`），只影响自己；管理员在同一个菜单里选择来源即设为这首歌的全站默认来源（标题为「切换全站歌词来源」，选「自动」取消），保存在表 `lyric_song_settings`（`PUT /api/v1/music/song/:id/lyric/pin`，仅管理员；读取随 `GET …/lyric/settings` 公开返回 `pin`），同时清除管理员自己在本地固定的来源，看到的就是全站的版本。

- 选择顺序（`contexts/song-lyrics.ts`，播放器页、悬浮小窗、导航栏与文章内的单曲卡、歌词摘录共用）：读者在本地固定的来源 → 全站默认来源 → 按质量自动选择；全站默认来源暂时没有歌词时同样按质量回退。
- 读者的菜单：有全站默认来源时「自动」显示为「默认（站长选择）」，该来源标注「站长选择」；管理员的标签上显示固定图标。
- 歌词缓存（7.2e）在已选用全站默认来源时缓存这一来源，打开时立即显示的就是全站看到的版本。
- 用途：管理员可以固定为标注了特效、调好了整体偏移（7.2l）的那一版，保证所有读者看到的一致。

### 7.2m 自定义粒子（AI 选图标或自己画）

内置的 18 种粒子场景表达不了歌词里一些具体、少见的意象（玩偶落下、纸飞机、糖果、风筝）。全曲规划可以定义最多 2 种自定义粒子（`sprites`），在出现意象的行上把场景写成 `custom:<name>`，与内置场景一样持续约 8 行、渐入渐出，只在播放器页与悬浮小窗演出。原型见 `docs/prototypes/lyric-effects/custom-particles.html`。

- 形状优先取自精选图标库：从 lucide 的 2171 个图标中人工挑出 223 个适合做粒子的（天空与天气、自然与植物、动物、食物、物件与玩具、音乐、爱与情绪、交通与旅行等 10 类），按类别列在规划的提示词里（约 540 token，固定前缀可被服务商缓存）；路径数据随后端打包（`lyric_sprite_icons.json`，附 lucide 的 ISC 许可说明），保存标注时写入粒子的路径。图标库里没有合适的，模型只描述意象（`image`），由一次单独的「画图标」请求画出 24×24 的简单剪影（1～4 条路径，主色 / 浅色填充或细线），与逐段标注并行，不增加总耗时；可行性实测：6 个意象（玩偶、纸飞机、糖果、风筝、鲸鱼、雨伞）一次全部通过校验且都认得出。
- 校验（`music_annotation_sprite.go`）：名称为小写字母数字；图标必须在精选图标库中；模型画的路径必须以 M 开头、只含绝对坐标的 M L H V C Q A Z 与数字，数字在 -1～25，每条不超过 600 字符，最多 4 条；动作只能取 fall（翻滚落下）/ float（上飘）/ drift（横向滑过）/ sway（原地摇摆后淡出）/ swirl（打旋落下）/ burst（从中部散开），尺寸 s / m / l，颜色取色板（无效时用默认值）。不合格的粒子丢弃，用到它的行改用模型给的备用内置场景（`fallback`）；没有行用到的粒子不保存。
- 渲染（`stage-particles.ts` 的 `spriteSpec`）：路径编译为 `Path2D` 后在已有的粒子画布上绘制，不往页面插入 SVG；图标库的线条线宽 2.5（lucide 原样的 2 在粒子尺寸下偏细），模型画的剪影按主色 / 浅色填充；尺寸 14 / 20 / 26 px（±20%），透明度上限 0.75，同屏最多 40 个，生成速率与轨迹由动作预设决定。
- 后台编辑：歌词特效编辑器中行的「粒子场景」可以选这首歌的自定义粒子；粒子本身不在编辑范围内，保存时原样保留。
- 实测（《莫愁乡》）：模型为「纸飞机掠过操场后」选了图标 `send`（横向滑过）、为一段童年回忆选了 `candy`（上飘）；《蝴蝶与鲸》里模型没有为鲸鱼定义粒子，用了内置的萤火与涟漪，克制使用符合预期。

### 7.2f 悬浮小窗的特效

悬浮小窗支持全部特效种类：字词特效、上色、字体字形、罗马音同步（共用歌词引擎）；背景呼吸、副歌爆发、染色、鼓点呼吸与 18 种粒子场景（`MusicStageEffects contained`：铺满小窗，粒子尺寸 ×0.7、最多 80 个），但不做镜头推近；封面取色、前奏导语与尾奏热评（字号更小）；AI 标志在生成中（首次生成或重新生成）时呼吸闪烁。

### 7.2g 新增：副歌片段

`GET /api/v1/music/song/:id/chorus`（公开）：网易云客户端在进度条上标出的副歌 / 高潮片段（NeteaseCloudMusicApi 的 `/song/chorus?id=`），`[{ "start", "end" }]`（毫秒），没有配置 API、请求失败或没有片段时为空数组；内存缓存（有片段 7 天、没有 1 天，出错不缓存）。

- 播放器页与悬浮小窗的进度条上用半透明色带标出这些片段。
- 实测每首歌通常只有一段（15～50 秒），是网易云挑出的最有代表性的一段副歌（不一定是第一段，如《咲き誇れ》在 2:41 的最后一段），不是全部副歌。
- 生成歌词标注时换算成歌词行（起点取开始时间最接近片段开头的行，3 秒内），在歌词行末直接标出〔高潮片段开始〕与〔高潮片段结束〕（全曲规划与逐段标注都能看到）；提示词说明这通常是一段副歌，同样的歌词在别处出现时一般也是副歌，模型据此找到全部副歌。只在生成时请求，不影响读取标注。

### 7.3 前端歌词数据模型

解析器（`ttml` / `yrc` / `lrc` 及翻译、音译）统一输出以下结构，再经过 8.8 的预处理后交给歌词引擎：

```ts
interface LyricWord {
  text: string
  start: number // 毫秒
  end: number
  romanWord?: string // 逐词音译（8.5）
  ruby?: { text: string, start: number, end: number }[] // 逐字注音（8.5）
}

interface LyricLine {
  words: LyricWord[]
  start: number
  end: number
  translation?: string
  romanization?: string
  isDuet: boolean // 对唱，右对齐
  isBackground: boolean // 背景人声，附着在上一主行
}

interface ResolvedLyrics {
  source: 'ttml-custom' | 'ttml-amll' | 'ncm-yrc' | 'ncm-lrc' | 'qq-qrc' | 'qq-lrc' | 'none'
  wordTimed: boolean
  lines: LyricLine[]
}
```

- 悬浮播放器与文章内单曲卡的歌词区已迁移到此模型（共用歌词引擎的紧凑模式）；导航栏与单曲卡标题处的单行歌词仍使用 `MusicLyricLine`，由 context 从最终选出的歌词转换（`toSingleLineLyrics`，只保留主唱行），与歌词舞台显示同一来源。
- 解析器、预处理与来源选择都是纯函数，放在 `web/src/lib/lyrics/`，用 vitest 覆盖。

### 7.4 状态层

- `MusicProvider` 仍挂在根布局，全站只有一个 `<audio>`，是播放状态的唯一来源；播放器页只是它的另一个视图。
- 拆分为：
  - **播放状态 context**：歌单、当前曲目、播放 / 暂停、模式、音量、解析后的歌词与翻译 / 音译开关，以及各种操作；value 做 memo。
  - **时钟订阅**：`useMusicClock(intervalMs)`，基于 `useSyncExternalStore`，供显示时间与进度条使用；歌词引擎通过 `getAudio()` 自行在 rAF 中读取。
- **当前歌词行**不放进 context value：与播放时钟一样是外部 store（`lyricCursor`），只在换行时通知，由 `useCurrentLyricIndex` / `useCurrentLyric` 订阅（导航栏单行歌词、单曲卡），换行不会让所有使用 `useMusic` 的组件重渲染；MediaSession 标题直接订阅当前行，最多每秒更新一次。
- 歌词获取（全部来源并发、按质量选择、只升不降）**全站统一**：`contexts/song-lyrics.ts` 按网易云歌曲 id 获取并缓存各来源（同一首歌只请求一次，最多缓存 100 首），按同一套规则（2.1～2.4）选出歌词。当前曲目由 `MusicProvider` 使用；文章内的歌词摘录（展示与编辑器选句）通过 `useSongLyrics(id)` 使用，并遵循读者为这首歌固定的来源。播放器页、悬浮播放器、导航栏单行歌词、单曲卡与歌词摘录因此总是显示同一来源的歌词（不会出现播放器是 AMLL 逐字、导航栏是网易云的情况）。
- 歌词摘录：作者手填的原歌词（LRC）优先；否则使用统一选出的在线歌词，快照文本与在线歌词对不上时只显示快照文本（宁缺勿错）。

## 8. 界面

### 8.0 页面与边界

- 唯一的音乐页面是 `/music`，一个沉浸式全屏播放器：播放控制 + 歌词舞台（布局见 5.1）。
- 播放列表内容**完全来自后台配置**，页面不提供任何增删改入口；列表只是给人看和点，本身不构成独立页面。
- 列表内提供**本地搜索框**：只过滤已加载的播放列表，不联网、不查任何音乐平台（见 8.11）。
- 不设艺术家页、专辑页、平台搜索页等入口；页内所有交互都围绕“当前这一首”展开。

### 8.1 歌词显示结构

一行歌词由四个渲染层组成，顺序固定：

1. 主歌词行（逐字/逐词）
2. 背景人声行（可选，可在主行上方或下方，见 8.6）
3. 翻译行（可选）
4. 音译行（可选）

硬规则：**翻译与音译是两个独立开关，不互斥**，同时开启时同时显示（见 5.3）；使用自己的字号、透明度，不挤占主行。

### 8.2 逐字扫词与强调

- **逐字擦除**：按当前行进度用遮罩从左向右揭示，边缘带羽化。羽化宽度以主字号倍数为单位：`0.5`（iPad 观感）/ `1.0`（Android 观感），不得为 0。
  - 遮罩只覆盖词自己的盒子：每个词上下留出 0.25em 内边距（负外边距抵消，不影响排版），未唱到的词里 g、y、p 的下伸部分与花体字不被裁掉。
- **已唱提亮**：高亮行叠两层副本（亮层 `mix-blend-mode: plus-lighter`、暗层镂空），亮/暗 alpha 为 `1` / `0.4`；浏览器不支持时降级为单层。
- **词强调**（已实现，`lib/lyrics/emphasis.ts` 计算分组，引擎逐帧演出）：满足条件的词按字符逐个“辉光放大 + 上浮”。
  - 规则（同 StarryPlayer）：按**词**判断，一个词唱满 1 秒、且少于 8 个字（拉丁文字还须多于 1 个字母）时强调，强度 = (min(时长, 2 秒) − 1 秒) / 1 秒。中日文用浏览器的 `Intl.Segmenter` 分词，词由若干逐字音节组成。
  - 浏览器分词与苹果系统不同（例如「怦然心动」会被切成「怦然 / 心 / 动」），切不出的成语、短语由歌词标注（7.2b）补上：标注的短语唱满 0.6 秒即演出，强度至少 0.3，可指定特效类型；与标注短语重叠的规则词让位给标注。
  - 特效类型：`swell` 放大（最多 1.14 倍）+ 辉光 + 上浮，左右的字轻微外推；`glow` 只发光、几乎不放大，适合温柔伤感的词；`wave` 不发光、逐字波浪上浮，适合轻快的词。
  - 起落曲线参考 AMLL：前半程较快升到顶点、后半程缓缓回落；演出时长至少 1000ms，字与字错开（时长 / 2.5 / 字数），上浮比辉光提前 400ms、时长拉长 1.4 倍；行尾一组加强 1.3 倍，副歌行加强 1.2 倍；背景人声行的上浮幅度翻倍。
  - 情绪基调（来自标注）决定辉光颜色：平静偏蓝、明亮偏暖黄、伤感偏紫、激昂偏红，颜色很淡，只带一点色温。
  - 被强调的词四周留出 0.3em 内边距（负外边距抵消，不影响排版），擦除遮罩改用像素坐标，放大的字与辉光不被遮罩裁掉。
  - **长音颤音**（`lib/lyrics/vibrato.ts`）：`shake` 短语中唱满 1 秒的最长音节记为长音。参考声乐研究——颤音约 5～7 Hz、幅度约 ±0.5～1 个半音；长音的颤音多在开唱后 0.2～0.5 秒才出现（约为音长的 12%～20%，音越长越晚），头几个周期幅度逐渐变大。因此长音开唱后先只按 `swell` 放大，延迟「音长 × 20%」（限制在 250～700ms）后整个词以 5.5 Hz 同步起伏（字间略有相位差），约 360ms 内渐强，放大保持到长音唱完，唱完后 300ms 内收住。没有长音的 `shake` 仍是快速细微的抖动（用于呐喊、愤怒）。
  - **消散 / 破碎 / 流光 / 心跳**（`lib/lyrics/word-effects.ts` 定义时间曲线，播放器、导航栏与全屏舞台共用）：
    - `dissolve` 消散：每个字唱完 150ms 后在 600ms 内淡出、变虚、向右飘，同时从字的位置生成细沙般的颗粒（`lyric-debris.ts` 碎屑层，叠在歌词上的 canvas，被风吹向右上方，约 2 秒消失）；正常播放时保持消散 12 秒（这一行通常早已滚出视野）再用 1.5 秒恢复；拖动进度、中途打开页面或换歌后，落点之前就该消散的字直接显示（引擎记录最近一次跳转的落点 `seekAt`，导航栏同样检测跳转），看到的是完整歌词。适合消失、离开、告别、梦醒。
    - `shatter` 破碎：消散的「一下子」版本，整个词唱完 60ms 后一起碎掉（不逐字）：碎之前 140ms 字以不同相位细微地颤（裂开的前兆，渐强）；碎时字立刻隐去，碎屑层把每个字以字内一个裂点为中心切成 6～8 块三角形碎片，每块带着原来的字形（按字当前的字体、颜色与缩放画到位图上），从裂点向外迸开（词左侧的字偏左、右侧的偏右）、旋转、受重力坠落，0.9～1.3 秒内淡出；全屏背景同时闪一下（`shatterFlash`，按 220ms 衰减）。之后同消散保持隐去 12 秒再用 1.5 秒恢复，跳转规则也相同；破碎总是一瞬间，不随特效节奏变化。适合心碎、梦碎、玻璃碎、誓言被撕碎、撞车。
    - `shimmer` 流光：唱到时一道光带从左到右扫过整个词（每遍 950ms，扫两遍）；扫动时字的颜色改由背景绘制并裁剪到字形（`background-clip: text`），光带叠在底色上。适合光芒、闪耀、星辰、彩虹。
    - `heartbeat` 心跳：整个词按「扑通-扑通」双拍放大（第二拍为 0.7、相隔 22% 拍长；约 0.75 秒一拍，至少 2 拍），左右的字随拍外推，辉光随拍闪；全屏背景也随拍跳动。适合心动、心跳、紧张。
    - 导航栏的简化版：心跳随拍轻跳；流光改为光带经过的词依次亮起（字太小，不画光带）；消散只淡出、变虚并右飘，不生成颗粒；破碎碎前同样细颤，碎时整个词在 0.2 秒内下坠淡出，不生成碎片（恢复规则同播放器）。
  - **特效节奏**（`lib/lyrics/pace.ts`）：歌词标注为全曲（`pace`）与个别短语（`phrases[].pace`）指定 slow / medium / fast，按歌词的轻快程度选择（规划给全曲定节奏，逐段只给与全曲不同的短语单独指定）；规则强调沿用全曲节奏。节奏只改变动效的快慢、不改变幅度：起落曲线时长 ×1.35 / ×1 / ×0.75（swell / glow / wave / focus 与背景呼吸），shake 抖动周期 70 / 45 / 30ms，长音颤音 4.8 / 5.5 / 6.5 Hz（延迟占音长 28% / 20% / 14%），心跳拍长 1000 / 750 / 520ms，流光每遍 1400 / 950 / 650ms，消散淡出 1000 / 600 / 350ms。播放器、导航栏与全屏舞台共用这套取值。
  - **下划线**：每个字在**所在音节**的演唱时段内画出（一个音节有多个字时平分），与逐字擦除同步；原来按整个短语的时长平均分给每个字，遇到拖长的音节时下划线会跑到还没唱到的字下面（被擦除遮罩压暗），唱到时才突然亮出来。
  - 「歌词特效」开关（控制栏，存本地，播放器页与悬浮播放器共用）；减少动态效果时始终关闭。
  - **导航栏与单曲卡的单行歌词**（`components/common/music-lyric-line.tsx`，样式计算见 `lib/lyrics/nav-emphasis.ts`）：开启歌词特效且为逐字歌词时沿用同一套强调分组（规则 + 标注），做幅度更小的简化特效——放大（最多约 1.08 倍）、辉光、上浮、抖动与长音颤音、由虚到实、标注的颜色与粗体 / 斜体；不做字体切换与下划线。减少动态效果时只上色。
- **词上浮**：普通词在行内按时间轻微上浮，背景人声行位移为两倍。
- **非逐字歌词**（仅有行时间的 lrc）：不做擦除，只做整行亮度与滚动。

### 8.3 行状态

| 状态 | 表现 |
|---|---|
| 高亮（正在唱或刚唱完） | 不透明度 `0.85` |
| 普通行 | `1` |
| 非动态歌词（纯行级） | `0.2` |
| 已唱且开启“隐藏已唱行” | 接近 0（用极小值而非 0，避免浏览器跳帧优化） |
| 视口外（含 overscan 外） | 不渲染，不透明度 `0` |

- **模糊**：按距焦点的行距分档（`1 + 距离`），上限 5px；窄视口（≤ 1024px）乘以 `0.8`；焦点行与触摸拖动期间不模糊。
- **缩放**：当前行放大，由弹簧驱动（值为百分比，`100` = 原始尺寸）。
- **阶梯入场**：同帧内多行位移动画逐行递增延迟（基础 `0.05s`），越靠后以 `1/1.05` 递减，形成错落感。
- 切换布局原因（播放推进 / 用户拖动 / 滚轮 / 跳转 / 重建 / 尺寸变化 / 配置变化）需分别决定是否禁用阶梯、是否重置间奏动画、是否瞬移不走近弹簧。

### 8.4 滚动、对齐与交互

- **对齐锚点**：`top` / `center` / `bottom` 三选一，配合容器高度比例位置（默认居中，约 `0.35`，可调）。
- **弹簧位移**：默认启用物理弹簧（重量 `1`、刚度 `100`、阻尼 `10`，均可调）；关闭后退回 CSS transition（低配降级）。
- **预渲染**：视口外保留 300px overscan 用于预构建，进入后才能逐字擦除不断帧。
- **用户滚动**：支持触摸拖动、滚轮单步、松手惯性；拖动时纵向位移直接跟随（不经过弹簧），松手后回归自动对齐；手动滚动期间冻结对齐焦点，不跟随播放进度。
- **跳转检测**：进度突变时自动判定为 seek，重置间奏动画并使用瞬移策略；可关闭。
- **单帧上限**：页面挂起后回归的单帧时间差钳制在 100ms，避免动画以数秒时长冲过头。

### 8.5 翻译、音译与注音

- **主次顺序**：原文、音译（发音）、翻译。字号比例参考 StarryPlayer（原文 48、音译 28、翻译 22）：音译 `0.58em`、翻译 `0.46em`（均不小于 10px），翻译不透明度 `0.5`、整行音译 `0.65`；紧凑模式（悬浮播放器、单曲卡）参考其小尺寸（原文 28、音译与翻译 18），二者均为 `0.64em`。
- **逐字音译（注音行，已实现）**：音译能对齐到原文音节时（`LyricLine.romanizationWords`），显示在原文下方：每个有音译的字组成一个注音单元（字在上、它的音译在下），一个字有多个音拍时连在一起显示（暖 → atata）。上游音译的空格不当作词的边界（网易云的整行音译、QQ 音乐的逐字音译都在每个音拍后加空格），音译里的标点与空白不显示（原文里已有）。排版（`lib/lyrics/ruby-layout.ts`，引擎测量时写入左外边距，网页字体加载完成后重新测量）：第一个音拍的中心对准字的中心（按文字本身的宽度）；音译不占单元宽度，可以伸到相邻的字下面，只有与同一排前一段音译的间距小于 0.35 个音译字号时才把这个字连同后面的内容往后推。音译的每一段按所在音节的时间与原文同步擦除；同一个音节分到的多段（多个音拍）没有各自的时间时，按字母数依次分配这个音节的时长，从左到右连续擦除（原来每段都占满整个音节，几段同时擦）。逐字音译的来源按可靠程度：TTML 的 `transliteration` 带时间分段（`xml:lang` 为 `*-Latn` 的一组优先，只有假名的读音不当音译；分段按开始时间对到音节，如「光」的 `hi ka ri`、「散」的 `chi`，见 `romanWordsFromSpans`）、QQ 音乐 / 酷狗的音译 QRC（按时间归到音节），最后才是按文字猜测（假名作锚点、汉字平均分音拍，相邻汉字之间可能分错，如「光散」→ hika / richi）。原来 TTML 的音译分段被压平成整行文字后再猜测，丢掉了上游给的准确对应。预处理去掉空音节时，逐字音译的音节下标随之重新对应。对不齐时整行显示在原文之下、翻译之上。
- **对齐规则**（参考 StarryPlayer 的 `LyricRomanizationAligner`，`lib/lyrics/romanization.ts`，宁缺勿错）：
  - 来源自带逐字时间的音译（QQ 音乐的音译 QRC）直接使用，按开始时间归到原文音节。
  - 纯汉字行（拼音、粤拼）：有内容的音节与音译词数量相同、且每个音节只有一个字时一一配对。
  - 含假名的行（日文）：假名与拉丁文字音节的读音（wanakana，含は / へ / を、づ / ぢ、长音的常见写法）作为锚点在音译字母中依次查找；锚点之间的字母按音拍分给其间的汉字音节（浏览器拿不到汉字读音；促音留下的单个辅音不单独算一拍）；多出的字母并入前一个音节。锚点找不到、或汉字分不到音拍时视为对不齐。
  - 纯拉丁文字、韩文等不对齐。
- **逐字注音（ruby，TTML 的注音音节）**：未实现。

### 8.6 对唱、背景人声与多行重叠

- **对唱（duet）**：该行改为右对齐，`transform-origin` 置于右侧；间奏点若紧接对唱行，跟随右对齐。
- **背景人声（BG）**：
  - 字号 `0.7em`（可调，最小 10px），不透明度 `0.4`
  - 与所在主行组成一个“行组”，附着在主行上方或下方（可配置为始终在主行下方）
  - 激活时从 ± 80px 弹簧滑入，缩放从 `0.8` 过渡到 `1.0`；未激活时折叠隐藏
  - 一行主歌词下方最多一个背景人声行；背景行可自带翻译与音译
  - 背景人声的时间需与主行同步
- **多行重叠 / 合唱**：高亮是一个集合而非单值；一行唱完不立即熄灭，会与后面重叠的行一起保持高亮；句间空隙内上一行继续保持高亮以维持可读性。
- **无意重叠清洗**：重叠达到 500ms 视为有意（保留）；不足 100ms 或不足下一行时长的 10% 时视为无意，把上一行结束时间截断到下一行开始。

### 8.7 间奏与底栏

- **间奏**：相邻歌词行的空隙 ≥ 7000ms 时判定为间奏，在空隙处显示三个圆点；间奏期间清空歌词高亮、把焦点交给间奏点，并与弹簧、缩放、透明度联动。
  - 圆点动效参考 StarryPlayer 的间奏倒计时（`lib/lyrics/interlude.ts`，按时间计算）：依次淡入（间隔 60ms、0.8 秒），先以 0.1 的低透明度出现；间奏开始 1 秒后按时间依次点亮，到结束前 1.8 秒全部点亮；期间在 1.2 / 0.9 倍之间交替呼吸（每拍时长按间奏长度均分）；结束前 1.8 秒先放大到 1.2 倍，1 秒后缩小到 0.2 倍并淡出，两侧的点以中间为原点收拢。减少动态效果时只保留透明度。
- **底栏**：歌词最底部固定一行（可插入任意内容，如制作信息、版权），默认不透明度 `0.2`，聚焦时 `0.85`；曲末聚焦底栏。

### 8.8 歌词预处理

解析后、渲染前统一过一遍优化：

- 归一化连续空格
- 行级时间戳补齐为字级时间戳
- 主行与背景人声时间同步
- 清洗无意重叠（规则见 8.6）
- **提前起唱**：最多提前 600ms，且与上一行没有重叠时最多提前到上一行结束（只用掉句间空隙；快歌里紧挨着的短行若都提前 600ms，会被提前到同一时刻、同时高亮，焦点停在最早的一行）；与上一行重叠时提前 400ms，重叠不足 400ms 则提前重叠时长的 70%

### 8.9 不雅用语打码

支持三种模式：不处理 / 全遮 / 保留首尾。遮罩字符可配（默认 `*`）。

### 8.10 动态背景

封面驱动的流体背景，从封面图提取调色板后渲染。参考实现提供三种渲染器（网格渐变 / Titanium / 隔离色块），均为 WebGL 着色器。第一期先用放大模糊的封面 + 压暗遮罩（CSS），WebGL 实现放在第四期，载体待定（见第 10 节）。

### 8.11 播放列表面板与列表内搜索

播放列表面板承担两件事：看当前列表、在当前列表内快速找歌。

- **数据来源**：后台配置好的完整列表，一次拉全，前端本地持有；不做分页请求、不做增量同步。
- **搜索范围**：仅当前这份列表，**不联网**，不调网易云 / QQ / 酷狗 等任何外部接口，不允许搜到列表外的歌。
- **可搜索的字段**：歌名、别名（网易云的别名与译名）、艺术家、专辑、歌曲 id；歌词等需要另行请求的内容不参与。
- **匹配方式**（`playlist-filter.ts`）：统一全半角与大小写，忽略空白、标点与符号，平假名与片假名视为相同；多关键词用空格分隔，全部命中才算命中（可分别命中不同字段）。
- **排序**：按相关度：歌名 > 别名 > 艺术家 > 专辑，字段与关键词完全相同、以关键词开头时加分，关键词是歌曲 id 时置顶；同分保持歌单顺序。悬浮播放器的小歌单与播放器页的抽屉共用同一套搜索。
- **交互**：输入即过滤，本地内存操作不防抖；无结果时显示空态文案；清空输入框恢复完整列表；结果项点击即播放该曲。
- **不影响队列**：搜索只是视图过滤，不改变原列表顺序、不改变上一首/下一首的取曲顺序，也不清空当前播放。
- 当前正在播放的那一首被过滤掉时**播放不受影响**，仅从列表视图隐藏。

### 8.12 性能约束

- 视口外不渲染、不跑动画
- 高亮提亮所需的双层副本仅在焦点前后 2 行范围内保留
- 行级延迟构建：进入可视区（含 overscan）才创建具体行内容
- 优先使用 `transform` / `opacity` / `filter`，避免触发布局
