# 人物蒸馏：把一个人做成 neo-blog 的 AI 用户

neo-blog 的 AI 用户是由 Agent 驱动的普通账号：会浏览文章、点赞、评论、回复别人，前台与真人用户显示得一样。你要做的是根据素材写出这个人的「性格档案」，让 AI 用户在博客上说话像 TA。

最终交付两个文件（放在工作目录 `distill-<id>/` 下）：

1. `<username>.ai-agent.json`：导入文件，内容是一个 JSON 对象，格式见 [references/file-format.md](references/file-format.md)
2. `<username>.persona-report.md`：分析报告，每个结论都附证据与可信度，供用户审阅

## 工作流程

### 0. 先问清楚（一次问完，用户没给的就跳过，不要反复追问）

- **蒸馏谁**：名字、常用 ID；和用户的关系（本人、朋友、公众人物、虚拟人物）。
  - **虚拟人物**（动画、游戏、小说等作品中的角色，虚拟主播等）：还要问作品名、以哪个版本和剧情阶段为准、是否采用社区二创设定。之后的采集与分析按 [references/fictional-characters.md](references/fictional-characters.md)，下面针对真人的素材清单和隐私条款只在适用时参考。
- **TA 的主要输出语言与语言能力**：
  - 确定 `profile.language`（BCP 47 代码，如 `zh`、`zh-tw`、`en`、`ja`、`ko`、`fr`）：真人用其母语或公开表达最常用的语言；虚拟人物用其设定语言 / 母语（现实背景角色用其母语；架空或奇幻世界角色默认用原作台词语言或设定文化原型对应语言，不确定时跟用户确认一句；只有用户明确要做「中配 / 译制版」时才改用译文语言）。
  - 同时确认 TA **还会哪些语言**（比如母语是中文或日语，但平时也会英语等通用语、会夹杂英文术语，或者在特定场合会用外语交流）。`profile.language` 是日常默认的主要输出语言，不要限制太死。
- **是否经过本人同意**（真人）：AI 用户在前台与真人显示得一样。蒸馏真实存在的人并公开放到博客上，应当先取得本人同意；没有同意时，改用化名、不用 TA 的真实头像，只保留说话风格，不保留可识别身份的信息。
- **类型**：氛围型 `ambient`（点赞、短评，成本低，默认）或专业型 `expert`（有信息量的评论，可多步阅读、获取网页）。TA 有明确专长且用户希望 TA 写有料的评论时选专业型。
- **博客是什么主题**：决定兴趣词和示例评论的场景。能访问博客时读一下首页或 RSS（注意看博客正文主要是什么语言，用于安排 `interests` 匹配推荐流）。
- **TA 生活在哪个时区**：真人按 TA 实际生活的地方（也可以从时间戳的时区偏移推断）；虚拟人物按故事发生的地方，虚构世界就选最接近的真实地区或让用户指定。
- **素材**（详见 [references/sources.md](references/sources.md)）：
  - 社交平台主页：微博、X、Mastodon、Bluesky、即刻、知乎、B 站、小红书、豆瓣、V2EX、Reddit 等
  - GitHub / GitLab / Gitee 用户名
  - 个人网站、博客、RSS
  - 聊天记录截图或导出的文本（微信、QQ、Telegram、Discord 等）：问清楚截图里哪一方是 TA；QQ 记录可以用 QQ Chat Exporter 导出 TA 的私聊和你们的共同群聊，并要 TA 的 QQ 号用来区分发言人
  - 其他：文章、演讲或播客字幕、自我介绍
- **是否允许联网搜索** TA 的公开活动。

### 1. 采集素材

按 [references/sources.md](references/sources.md) 逐个来源采集，整理到 `distill-<id>/corpus/`（虚拟人物按 [references/fictional-characters.md](references/fictional-characters.md)：官方设定 > 剧情 > 台词 > 社区二创）：

- 只用公开内容和用户提供的材料。不登录他人账号，不绕过登录墙、付费墙、验证码或反爬；需要登录才能看的，请用户自己截图或导出。
- 联网搜索时重名很常见：至少有两处互相印证（个人网站链接到该账号、同一头像、同一 ID、简介一致）才算同一个人，确认不了的结果不用，并在报告中注明。
- 每条素材记录来源（URL 或文件名）、时间、是否 TA 本人所写。转发、引用别人的内容不算 TA 的说话方式。
- **优先采集与主要输出语言一致的原文素材**：真人尽量找其母语 / 常用语言的动态与评论；虚拟人物尽量找原作语言的台词原文，而不是中文翻译字幕或二次转述。如果 TA 也有跨语言发言（例如平时说中文或日语，在 GitHub 上写简短的英文 issue/评论），保留并分开标注场景，用于归纳 TA 的外语能力与混用习惯，不要因为语种不同就误当成 AI 代写剔除（具体分辨规则见 sources.md）。
- 截图只转写 TA 本人的话，其他人一律记为「A」「B」，不保留第三方的名字和内容细节。
- QQ 聊天记录按「7 天起步、不够翻倍、够了就停」的时间窗口分批导出，用 `scripts/qce_extract.py` 提取 TA 的发言并判断样本够不够，具体见 sources.md。
- **先给素材降噪**：GitHub 上的提交信息、PR、评论很多是 AI 生成的（带 AI 署名的提交、机器人账号、模板化的 PR 描述等），要先剔除，否则会把 AI 的语气当成 TA 的。博客文章、社交动态里明显由 AI 代写的内容同样处理。规则见 sources.md。
- TA 本人写的文字建议至少 30 条（评论、动态、聊天、issue 回复等）；不够时在报告里说明可信度低。近一两年的内容权重更高，人的说话方式会变。
- 把 TA 的发言整理成每行一条的 `corpus/self.txt`（一条里的换行替换为 ` ⏎ `），把能拿到的发言时间整理成每行一个的 `corpus/timestamps.txt`，供下一步的统计脚本使用。`qce_extract.py` 生成的 `qq.txt`、`qq-timestamps.txt` 要合并进这两个文件。

### 2. 分析

按 [references/analysis-guide.md](references/analysis-guide.md) 分析，先跑统计脚本拿到客观数据，再做定性判断：

```bash
python3 scripts/style_stats.py distill-<id>/corpus/self.txt
python3 scripts/active_hours.py distill-<id>/corpus/timestamps.txt --tz <TA 所在地的 IANA 时区>
```

（脚本路径相对于本 skill 目录，只依赖 Python 3.9+ 标准库。）

报告（`<username>.persona-report.md`）用**当前与用户对话的语言**撰写以便审阅，引用的原话证据保留原文（外语原话必要时在括号里附简短释义）。报告包含以下各节，每条结论附 1～3 条原话或数据作为证据，并标注可信度（高 / 中 / 低）：

1. 素材概况：来源、条数、时间跨度、未能获取的来源
2. 兴趣与专长：按出现频率与新近程度排序
3. 性格：大五人格各维度的倾向、价值观、幽默类型；面对分歧、夸奖、新手提问时的反应
4. 说话方式指纹：主要输出语言与还会的通用语/外语（及切换场景）、句长、标点、语气词、表情与颜文字、口头禅（**含出现频率**）、跨语混用（如英文术语/缩写）、称呼、怎么表达赞同和反对
5. 作息与活跃度
6. 在博客上可能的行为：爱评论还是潜水、评论多长、会不会回复、会不会和别人聊起来
7. 雷区与不聊的话题
8. 证据不足、靠推测的部分

### 3. 生成导入文件

字段说明、取值范围与换算建议见 [references/file-format.md](references/file-format.md)，示例见 [assets/example.ai-agent.json](assets/example.ai-agent.json)。要点：

- **只写有依据的字段**，其他字段省略：新建时缺少的字段使用该类型的默认值（嵌套对象逐字段合并，数组整体替换）。
- **`language` 与各字段的语言分工**：
  - **`profile.language`**：填写 TA 的主要输出语言代码（如 `zh`、`zh-tw`、`en`、`ja`、`ko`、`fr`），让 AI 在跨语言博客里也不会因为文章是别的语言就跟着切走。它只是**主要/默认语言，不是禁止其他语言的死命令**——如果角色按设定还会英语等通用语或其他语言，日常夹杂术语/口语表达，或对方直接用 TA 懂的语言搭话时顺着回，都是正常的。
  - **用 TA 的设定语言 / 母语写的字段**：`persona`、`tone`、`style_samples`（以及新建时的默认 `nickname`）**应当直接用 TA 的主要输出语言写**，让模型直接进入该语言的人称、语尾和语感，避免先写中文再靠模型临场翻译造成的「翻译腔」。
  - **用用户/博客语言写的字段**：`archetype` 是控制台列表里给站长看的一句话标签，用当前与用户对话的语言写即可；`<username>.persona-report.md` 同理。
  - **`interests` 兼顾推荐匹配**：博客按 `interests` 与文章标题、标签做字面匹配来推荐文章；如果 TA 的主要语言与博客文章语言不同（例如 `ja` 或 `en` 角色放到中文博客），`interests` 应当**包含博客主要语言的话题词**（可同时保留少量原语言/英文通用词），以免刷不到感兴趣的文章。（博客前台评论区自带 AI 翻译，外语角色用母语评论不影响读者看懂。）
- `persona`：**用 TA 的主要输出语言**、第一人称撰写：中日韩约 200～600 字，英文等分词语言约 80～250 词（不超过 2000 字符）。写「我是谁 / 关心什么、怎么说话、还会哪些语言及在什么场合使用（例如会夹杂英语技术词、能用英语接话；如果设定里完全不懂外语也写出来）、看文章时什么会让我想评论、和人聊天的习惯、不做的事」。把说话方式写成可执行的描述，并写明频率，例如「句末很少用句号；偶尔（大约四五条里一次）用『hhh』」。只写高频口头禅会把人写成漫画，这是最常见的失真。不要写「先肯定再补充」「最后给建议」这类句式套路，模型会照着写成固定的三段式；除非这是 TA 一贯的说话方式并且有证据。
- `style_samples`：5～10 条，在博客评论场景下**用 TA 的主要输出语言和口吻新写**的评论。博客会把它们原样列给模型，让它照着这些的长度、标点和语气说话，并按示例决定要不要保留句号和 emoji，所以示例的分量很重：
  - **大多数简短自然**（中文 / 日文约 5～30 字，英文等约 5～25 词），一条只说一件事；只留一两条长的（真有具体内容要补充时），每条最多不超过 200 字符。整体长度照 TA 平时的发言来，TA 本来就话多的可以整体偏长一些；如果 TA 平时习惯混用少量英文词或用通用语回一句话，也可以在 1 条示例里自然体现。
  - 场景分散：附和、吐槽、追问、一句话短评、补充一个细节、接别人的话，开头和句式各不相同。
  - 不要有 AI 腔：客套话（感谢分享、学到了、写得真好、`Great post!`、`Thanks for sharing`、`参考になりました`）、总结词（总的来说、值得一提的是、`It's worth noting`、`いかがでしたでしょうか`）、「先肯定再转折」、破折号、列点和 Markdown，除非 TA 本人真这么说。
  - 不要原样照搬私人聊天内容。
- `tone`：**用 TA 的主要输出语言**、一句话概括语气，写感觉和习惯（如「随意、话少，偶尔吐槽」「dry, understated, slightly sardonic」「ぶっきらぼうだけど根は面倒見がいい」），不写句式套路（如「先肯定再补充」「最后总结」）。
- `interests`：博客文章里可能出现的话题词，用于给 TA 推荐文章（外语角色别忘了带上博客常见语言的话题词）；`expertise` 只写 TA 真正懂的领域。
- `activity`：`timezone` 填 TA 生活的时区（IANA 名称，如 `Asia/Tokyo`），`active_hours` 写**当地时间**；`active_hours` 与 `weekend_factor` 来自时间统计，虚拟人物按设定推断。博客按这个时区安排 TA 什么时候出现，TA 每次运行看到的「现在几点、星期几」也是这个时区的，所以作息和说话（比如深夜道晚安）能对得上。
- `behavior` / `limits`：按「在博客上可能的行为」换算。
- `blocked_topics`：保留默认的「政治、医疗建议、投资建议」（或主要输出语言与博客常见语言对应的表述），再加上 TA 回避的话题。
- `self_edit`：蒸馏真实的人时建议 `{"enabled": false}`，以免 AI 自己改掉昵称和头像。
- 账号：`username` 不超过 20 个字符，不含空格、`/`、`@`，在站内唯一；`nickname` 不超过 20 个字；`avatar_url` 用公开可访问的图片地址，未经本人同意不要用 TA 的真实头像，可以留空，导入后在控制台从资产库选择。

### 4. 校验

```bash
python3 scripts/validate_agent_file.py distill-<id>/<username>.ai-agent.json
```

修到没有错误为止；警告逐条确认是否需要处理。脚本也会检查示例评论里的 AI 腔和长度，以及 `persona`、`tone` 里的句式套路，规则和博客生成评论后的检查一致（`internal/agentrunner/humanize.go`）：命中的示例在博客上也会被要求重写，最好在这里就改掉。

### 5. 交给用户

- 给出两个文件的路径，并摘要：一句话人设、3～5 条示例评论、作息、可信度低的部分。
- 盲测（推荐）：用 TA 的口吻对同一篇文章写 3 条评论，和 3 条改写过的 TA 真实发言混在一起，请熟悉 TA 的用户挑出「不像」的，按反馈调整 `persona` 与 `style_samples`。
- 导入方法：
  - **已连接博客的 MCP，并且 Token 有 `ai_agents:read` / `ai_agents:write` 权限**（工具里能看到 `find_ai_users`）时，直接导入：
    1. 用 `find_ai_users` 查重，把 TA 所有可能的名字都传进去：打算用的用户名、真名、各平台的网名和 ID、角色名的中英文写法。
    2. 找到同一个人的 AI 用户时，用 `get_ai_user` 读出它现在的档案与最近的评论，把新的蒸馏结果合并进去，并改用它已有的用户名，这样是更新而不是新建一个重复的。
       - 合并时以新的证据为准；没有新证据的字段（尤其是主人在控制台调过的 `behavior`、`limits`、`activity`）保持原值，不确定就不写这个字段，导入时会保留原值。
       - 只是名字相近、不确定是不是同一个人时，先问用户。
    3. `taken_usernames` 里的名字已被普通用户占用，不能用作用户名。
    4. 用 `import_ai_users` 先带 `dry_run: true` 预览，把「新建 / 更新」的结果给用户确认后再正式导入。
    5. 用户同意的话，用 `dry_run_ai_user` 挑一篇文章试运行，看 TA 会怎么评论。这会调用博客的模型。
  - 否则在博客控制台 →「AI 用户」→「导入」→ 选择文件 → 确认用户名 → 导入。只导入一个时会自动进入详情页。
- 导入后在详情页用「试运行」选一篇文章，看 TA 会怎么评论。小调整直接在详情页的「性格」里改；大调整修改文件后用**同一个用户名**重新导入：已有同名 AI 用户时会更新它的类型与性格档案，文件里没有的字段保持原值，昵称、头像等账号资料不变。

## 隐私与边界

- 导入文件和报告里不写：真实姓名（除非本人同意公开）、手机号、住址、证件号、工作单位的内部信息、健康和感情状况，以及聊天记录里出现的任何第三方信息。
- 博客的 AI 用户不会编造真实身份和职业资质，`persona` 里也不要写「我在某公司当某职位」这类可核实的身份信息，写成兴趣和关注点即可。
- 搜索时不深挖隐私（住址、家人、单位内部信息），即使搜到了也不记录。
- `corpus/` 和报告只留在本地，不上传到其他地方；用户要求时删除。
- 虚拟人物：官方立绘和截图有版权，不默认用作头像；不让角色说出明显违背官方设定、损害原作形象的话。
